## 4. S05-H01：统一宿主人格设置

### 4.1 用户最终体验

N.E.K.O 的人格设置显示铃芽中的当前段落、草稿 revision 和已发布版本。用户可在宿主修改段落、保存草稿、显式发布；铃芽立即看到相同结果。草稿保存不改变正在使用的已发布人格，发布后下一轮才采用。外观、模型、音色、工具与插件配置仍属于宿主。

### 4.2 主要改动位置

| 仓库 | 目标模块 |
|---|---|
| N.E.K.O | `main_routers/characters_router/cards.py`、`persona.py`；`main_logic/engine_persona.py`、`remote_memory.py`、`remote_memory_router.py` |
| N.E.K.O 前端 | `templates/character_card_manager.html`；`static/js/character_card_manager/card-form-and-actions.js`、`character-data-and-transfer.js` 及实际负责该保存行为的模块；`character_personality_onboarding.js` 按入口影响修改 |
| companion-memory | `service/management.py`、`server.py`、`stack_config.py`、`host.py`；复用 `domain/persona_card.py`、`persona_admin.py`、`persona_publish.py` 的既有业务方法 |

### 4.3 实现步骤

1. 列清宿主现有的人格输入、预设选择、系统提示词、导入及保存入口。仅处理会改变当前服务角色语义的入口，不重做完整角色卡交换或资源管理。
2. 在现有宿主角色设置内使用服务实际的 `section_id/kind/text/editable_by/frozen/revision` 编辑；避免把多个段落压成一个文本，再按旧 `host_字段名` 覆盖整张卡。保留未修改段落的 ID、范围、冻结和可编辑性。
3. 旧语义控件改为操作这个编辑区，或明确停用并指向服务编辑区；不能留下一个看似保存成功、生成时却不会读取的旧人格编辑框。头像/模型等资源控件继续工作。
4. 增加宿主到服务的受限人格管理能力。优先用服务端明确的当前角色人格读/改/发布路由，例如 `GET/POST /v1/host/persona` 与 `POST /v1/host/persona/publish`，内部只委托既有领域服务。最终方法、字段、错误码回填 `webui-console.md`。
5. 当前普通宿主身份不是管理员，不能直接调用现有全部管理 API。只为显式配置的宿主身份授予必要的人格操作能力，默认关闭；配置解析、身份判定和服务路由共同校验角色/主体和权限。不要全局放开 `/v1`，不要让宿主自动领取 console 管理令牌，也不要把令牌交给浏览器。该能力不注册为模型工具。
6. 宿主浏览器通过同源后端操作，沿用本地访问/Origin 防护；服务地址和身份来自新配置，不接受页面任意指定上游 URL 或角色。
7. 打开编辑器时固定 `base_revision`；提交时原样携带。服务返回 409 时保留草稿并展示当前版本，用户比较后再保存。禁止提交前悄悄读取最新 revision 后覆盖，也禁止自动演化竞争失败后落回 `characters.json`。
8. 分开“保存草稿”和“发布到下一轮”。发布提交用户实际看到的 revision；如果草稿已变化，返回冲突并保留编辑内容，不能发布另一版。人工编辑、冻结与演化的权限语义复用核心现有规则。
9. 角色语义与宿主资源保存分开：资源保存不能触发人格导入/发布；人格失败不能用资源保存的成功响应掩盖。若一次界面操作提交两类修改，分别返回结果，不承诺跨两端的原子事务。
10. 读取失败或写入失败时显示具体失败并保留草稿。缺少模型凭据不应阻止人格编辑；不使用旧配置补齐服务人格。

### 4.4 完成条件

- 宿主与铃芽显示同一张卡，宿主保存后铃芽可读，重启后保持。
- 保存草稿期间，普通文字生成继续使用原发布版本；显式发布后下一轮采用新版本，在途轮次不切换。
- 两个编辑页面或自动演化引发 revision 冲突时，旧草稿仍在，服务最新内容不被覆盖。
- 无权限身份与跨主体/跨角色请求被拒绝；资源修改不会改变人格、演化模式、凭据或未编辑段落。
- 关闭服务再保存，得到失败提示，宿主没有写入一份替代人格并报告成功。

## 5. S05-H02：连接与保存状态可见

### 5.1 用户最终体验

聊天页能区分：服务已连接、本轮正在生成、本轮已经保存、待同步、生成中断、记录已失效或保存失败。页面刷新与后台补交后状态会更新。服务已连接不等于本轮已保存，队列清空也不等于历史失败已成功。

### 5.2 主要改动位置

`main_logic/remote_memory.py`、`main_routers/remote_memory_router.py`、`static/app/app-websocket.js`、`static/app/app-chat-adapter.js`、`frontend/react-neko-chat/src/` 中的实际消息状态与共享聊天组件；必要时修改服务的健康/请求/消费回执响应。人格发布采用状态继续复用铃芽的 `service/console.py` 和 `webui/designs/tidebell/live.js`。

聊天 UI 只有一份 React 实现；同时验证网页主页浮层和 `/chat` 独立页面，不能复活旧 `#chat-container`。

### 5.3 实现步骤

1. 扩展现有状态接口，保留启动器校验所需的 `character_id/host_root`，增加真实服务探测结果、最近成功时间/错误码、待提交轮次数、待显示回执数、终态失败摘要与实际采用版本。不要返回令牌、模型密钥、原始提示词或聊天正文。
2. 区分“未配置”“连接检查中”“无法连接”“存储/上下文不可用”和“可用”。不能继续在只读到本机配置时返回健康连接，也不要把 401/403 一概当断网重试。
3. 健康探测有期限，使用 internal HTTP client，不占用整轮生成锁，不在事件循环做同步磁盘/网络操作。前台可做有界轻量刷新，隐藏或断开后降低频率；不新增监控服务。
4. 服务 `/v1/health` 的 chat 项描述服务自身的对话模型。宿主可用独立模型，不能仅因服务 `/chat` 模型不可用就错误停掉“宿主生成 + 服务存储/上下文”路径。按实际依赖判定能力。
5. 将原生前端 request/speech 标识与 memory request/turn 标识明确关联，保留固定首次发生时间、版本和作用域。不能用“当前最后一条气泡”关联迟到回调。
6. 为每轮保存结果提供稳定语义：已持久提交才显示“已保存”；待补交显示“待同步”；删除/更正后的终态失效显示相应原因；中断与保存状态分别表达。保留必要的有界、无正文结果元数据，支持刷新后恢复，不能再保存一份权威聊天历史。
7. 后台补交成功或失败后通过现有消息桥或轻量状态刷新更新页面；不能只在最初 `COMPANION_TURN` 到达时显示一次状态。现有 `saved=false` 必须有可见结果。
8. 区分模型生成、持久提交、用户实际看到。显示回执在对应消息已进入实际 React 展示后产生；不能只依据收到一个状态通知或 `reply_chars` 就声称整条回复已显示。
9. 显示回执带固定 receipt ID，暂时发送失败时有界重试并可刷新恢复；后台重复确认不得产生新聊天、重新生成或重新播放。实际显示的是前缀时，只确认该前缀。字符数对齐服务的 Unicode 字符计数，覆盖 emoji；禁止用 JS UTF-16 长度直接冒充服务字符数。
10. 来源已失效后，旧上传和回执应终止并清除关联正文；不能反复补交、恢复已删除内容，也不能让一条失效显示回执永久阻塞下一轮聊天。复用当前队列对此的终态处理。
11. 提示面向用户说明“能否继续聊天、是否已经保存、可做什么”，不要把内部队列文件、异常栈或接口名称放入聊天气泡。

### 5.4 完成条件

- 停服务、错误身份、存储不可用与正常连接显示不同结果；恢复后状态自动回到实际值，草稿不消失。
- 人为丢失一次提交响应，页面先待同步，后台同键回放后变已保存，服务只多一轮，模型只调用一次。
- 宿主重启后仍能识别待补交与终态失败；不会把未完成的生成当完整回复。
- 显示回执丢失、重复、乱序、刷新与包含 emoji 的回复都有正确归属；晚到旧回执不修改新气泡。
- 删除/更正与补交竞争时，正文不复活，失败状态可理解，后续正常聊天不被卡住。

## 6. S05-H03：文字主动交流接入同一服务

### 6.1 用户最终体验

开启文字主动交流后，小潮沿用当前已发布人格和相关记忆来主动找话题；你开始说话时它让出对话。实际发出的文字可在铃芽中追踪，没发出去的候选不被记成已经告诉过你。整个过程没有语音和自动屏幕采集。

### 6.2 主要改动位置

| 职责 | 入口 |
|---|---|
| 主动请求与调度 | `main_routers/proactive_router.py`、`main_logic/proactive_chat/service.py` 及现有 contracts/state/decisions 模块 |
| 模型生成与旧语义读取 | `main_logic/proactive_chat/generation.py`；service 中的 `lanlan_prompt_map`、`new_dialog`、followup/topic 读取 |
| 实际提交、抢占与结束 | `main_logic/proactive_chat/delivery.py`、delivery pipeline；原生会话的 proactive delivery/owner 方法 |
| 临时指令生成路径 | `main_logic/omni_offline_client/_lifecycle.py` 的 `prompt_ephemeral`，以及实际被选中的主动生成路径 |
| 远程上下文与提交 | `main_logic/remote_memory.py`；服务 `server.py/protocol.py`、已有 TurnRequest/TurnCommit 和来源分类 |
| 采用状态与 UI | 服务 console、铃芽 live.js；宿主共享聊天组件与状态桥 |

先沿真实调用链确认哪条路径负责本轮生成和展示；不能只给一个未被使用的方法加装饰器后宣告接通。

### 6.3 实现步骤

1. 复用既有空闲判断、频率、冷却、用户活跃、goodbye silent、外部路由占用与 `ProactiveLifecycle`，不另做调度器。默认不替用户开启主动交流。
2. 将远程客户端的通用能力拆成可复用的“取上下文/登记本轮/保存结果/上报回执”，允许指定来源与消费者；不要将普通聊天装饰器原样套到主动流程，复制其历史替换、普通用户输入和全程锁定行为。
3. 使用独立消费者，建议 `neko_active`；普通聊天仍为 `neko_chat`，网页仍为 `chat`。服务保留客户端来源，避免一次主动采用覆盖聊天的采用状态。铃芽标签清楚标出来源，不同时展示一个重复的假“主动交流未接入”占位。
4. 人格、关系、相关记忆、更正与禁提约束从服务读取。优先复用 `/v1/context`，按需要显式传递主动用途并复用核心预算/候选方法；确需候选路由时做薄封装，不在宿主扫描服务存储或复制召回算法。
5. Phase 1 里凡是参与人格判断的输入和 Phase 2 实际生成使用同一轮固定发布快照。开始真正生成前登记、校验依据；发布新版不改在途快照，下一轮才换版；删除/更正使依据失效则终止旧生成或送达。
6. 移除这条远程主动路径上的 `lanlan_prompt_map`、旧 `new_dialog` 与宿主本地长期记忆/禁提指令兜底。宿主可保留防重复与冷却等短期展示状态，但不能据此创造另一份人格或事实权威。
7. 明确来源分类：真实用户发言才按 chat/preference 等用户来源处理；自动主动输出按现有 `companion_output` 等合适类别保存，不能作为新的用户偏好证据。内部“主动关心用户”的指令、候选标签、工具结果、模型自述和截图描述都不能伪装成真人发言。
8. 主动轮次没有本轮真人输入时，使用明确的系统来源/触发元数据，保留实际可见回复；若沿用整轮接口所需的 system 消息，只放最小类型标识，不存入长提示词。不得为了凑 `messages` 而伪造一句“用户要求主动交流”。
9. 生成、内容筛选、实际展示、存储与回执分开：未生成、被筛掉、取消前未显示、部分显示、完整显示必须走明确终态。只有实际显示的文字才成为“已对用户说过”的内容。无法展示的候选不得写入 recent 冒充可见 AI 回复。
10. `used` 继续描述实际使用版本，`delivered` 描述实际显示；读取或预热不是采用。若需要记录被过滤生成的版本使用，用无正文审计表达，不为满足回执前置伪造完整聊天记录。
11. 保留当前 reserve、幂等提交与队列恢复。重试存储只重发原 ID、原时间、原版本和原正文，不再次生成或再次弹出气泡。队列满或服务必需上下文不可用时，本次主动交流跳过并显示/记录准确原因，不用旧人格继续。
12. 用户优先：新用户输入到来时，尚未显示的主动内容应取消；已显示前缀按真实内容收尾。迟到回调只处理自己的轮次，不替换新轮的 history/instructions，不复用新轮 request ID。
13. 当前客户端锁跨普通生成持有。主动接入时必须检查该锁是否阻塞用户抢占；只锁必要的队列读写或服从宿主已有所有权协议，不让主动模型等待和网络超时长期占住用户入口。
14. 停止/取消/重连/失败都让既有生命周期结束一次；不遗留“正在主动生成”的状态或重复安排重试。继续保留远程入口对旧首次见面脚本的跳过，直到它真正进入同一条受控链路。
15. 本包只做文字。禁用语音送出，不借助音乐、屏幕截图或外部新闻证明接入成功；Live2D 可沿用现有文本触发的表情表现。

### 6.4 完成条件

- 在隔离角色中准备已知记忆与语气，显式触发一次文字主动交流；实际模型请求包含正确版本/记忆，铃芽显示对应来源、原文和正确消费者。
- 发布新版后下一次主动生成采用新版；正在进行的旧轮不混用新旧文本。普通聊天的采用记录独立保持。
- 用户在主动生成中发言，普通聊天能接管；取消的主动轮没有迟到覆盖或重复气泡，生命周期不挂住。
- 自动指令和 AI 主动内容不增加用户偏好的支持次数，不推动无依据的人格演化；真实用户随后明确表达的偏好仍正常入库。
