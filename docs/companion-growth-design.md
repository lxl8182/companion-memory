# 面向养成感与活人感的记忆系统设计

日期：2026-10-27。本文整合前面的 QQ 对话链路排查、四条记忆链路讨论、明确教导与模仿学习需求，并对照公开的陪伴产品、记忆框架和研究设计。

**推荐保留现有 companion-memory 核心，补齐“明确教导立即采用、共同经历持续积累、自主认识逐步成熟、相关记忆改变当前行为”四件事。** 检索采用分层上下文与混合召回；向量用于补足语义关联。养成的主要载体应是有来源的相处规则、共同经历、关系变化和持续兴趣，再由其中稳定的部分修订人格卡。

本文是新的语义设计与实施依据；工作包状态继续只在 [roadmap](roadmap.md) §2.6 维护。传输、输出保存与发布流程沿用 [陪伴连续性实施方案](companion-continuity-plan.md)，远程宿主采用 [远程记忆宿主方案](remote-memory-host-plan.md)。本文对“明确教导快速采用”的规定，补充并细化旧方案中的反馈与演化规则。

## 1. 要让用户实际感受到什么

养成感来自可感知、可追溯的改变：

- 我教过她某种说话方式，下一次她就开始这样做，过几天也延续。
- 我们共同完成过某件事，之后提到它，她能想起过程、结果和当时的互动。
- 相处久了，她形成自己的兴趣、习惯和判断，但仍然认得出是原来的角色。
- 新的交流能修正旧认识，我不必反复重教，过去的误解也不会总是冒出来。

活人感来自连续的注意力与合适的行为：

- 接得住“后来呢”“那个又出问题了”，也能察觉话题已经结束。
- 知道什么时候接话、开玩笑、安静听、给建议或稍后跟进。
- 记得双方说过的话与约定，主动交流有具体缘由。
- 表达保有个性和变化，少用固定客服句式、机械复述和每轮追问。

因此，评估重点是“记忆让后续行为发生了什么变化”。事实数量、摘要长度、亲密度数字和检索分数只帮助诊断局部问题。

## 2. 成熟方案怎么设计，值得借鉴什么

下表按公开机制比较产品和框架。商业陪伴产品更适合参考交互形态；基础框架更适合参考证据、存储与召回机制。

| 方案 | 公开设计重点 | 对本项目最有价值的借鉴 | 本项目的采用方式 |
|---|---|---|---|
| Kindroid | 背景设定、关键记忆、回复示例和指令；Learned Context 分为成长与关系、重要事实、未完话题；短期、中期、长期记忆分工 | 陪伴所需的长期上下文应包含“我们怎样相处、正在关心什么”；示例直接塑造表达 | 增加三个简短投影视图，采用明确风格规则与示例；内部级联算法按公开产品行为理解 |
| Hindsight | 原始事实归并成有依据的 observations；mental models 保存持续问题的整合认识；多路召回 | 反思需要更新旧认识、处理反证，并保持证据可追溯；长期理解可以预先整理 | 复用现有反思存储和后台维护，建立按主题更新的认识；保留引用与失效重建 |
| Mem0 | 近期公开算法采用单次提取、ADD-only 历史记录、实体关联与多信号召回 | 原始历史与当前状态分开，重复提及和状态变化都值得保留来源 | 保留原事件，生成当前事实视图；同一事实增加真实来源，不增加镜像和重试次数 |
| Zep / Graphiti | 实体、关系、episode；区分现实有效时间与系统记录时间 | “以前喜欢、现在不喜欢”和“昨天说的明天”需要时间合同；经历能串起事实 | 在现有存储补时间与关联字段；当前规模优先使用 SQLite 和显式关联 |
| Letta | SDK 有 persona / human 等记忆块；当前 Letta Code 有显式记忆指令和后台 dreaming / consolidation | 用户明确要求记住与后台自行整理应走不同路径；区分角色设定与用户认识 | 教导快速采用，后台异步归并；沿用本项目单写者、版本发布与删除机制 |
| Honcho | 持续形成用户表示，提供工作摘要和按需的深层查询 | 对用户的理解应成为独立对象，并可随交流纠正 | 分开存“我是什么样”“我如何理解你”“我们怎样相处”，避免把用户偏好写成角色身份 |

来源：[Kindroid 记忆](https://kindroid.ai/v2/docs/memory/)、[人格与回复示例](https://kindroid.ai/v2/docs/customizing-personality/)；[Hindsight observations](https://hindsight.vectorize.io/developer/observations)、[mental models](https://hindsight.vectorize.io/developer/mental-models)、[retrieval](https://hindsight.vectorize.io/developer/retrieval)；[Mem0 当前提取与检索算法](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)；[Zep facts 时间模型](https://help.getzep.com/facts)；[Letta SDK 记忆块](https://docs.letta.com/v1-sdk/memory/memory-blocks)、[Letta Code memory & dreaming](https://docs.letta.com/configuration/memory)；[Honcho 官方文档](https://docs.honcho.to/)。

研究中，[Generative Agents](https://arxiv.org/abs/2304.03442) 把经历、带来源的高层反思与行为规划接起来；[LongMemEval](https://arxiv.org/abs/2410.10813) 强调跨会话理解、知识更新与时间推理。这些工作支持本项目把验收从“是否取到一句相似文本”扩展到“是否沿着时间、人物和经历给出合适回应”。

### 2.1 最应该采用的五项设计

1. **明确教导与自主学习分流。** 用户授权的持久改变直接进入可用规则；系统自己推断的改变积累证据。
2. **保留共同经历。** 记录双方行为、结果、情绪表达和后续影响，事实抽取只是其中一个视图。
3. **维护可更新的认识。** 新信息可能补充、反驳或收窄旧认识；反思任务可以没有新结论。
4. **给当前关系一个小型工作摘要。** 成长与关系、重要事实、未完话题分别整理，按需要注入。
5. **让回忆连接行动。** 召回后选择回应策略、兑现约定或安排跟进，记录真实反馈再调整。

### 2.2 当前阶段的技术选择

继续使用现有 Python 核心、JSON/SQLite、事件日志、outbox、删除屏障和人格版本。先修数据语义和消费链路，再按召回样本接语义向量。当前不引入独立图数据库、多套记忆服务或多代理反思体系。

外部系统的 benchmark 用来挑选评测维度。本项目的选择以中文陪伴对话、跨天续接、明确教导和真实使用反馈为依据。

## 3. 当前实现的优势与关键缺口

### 3.1 可以直接复用的基础

现有核心已经覆盖事实、反思、成长、人格卡修订、发布、回滚、状态、混合召回、删除更正及后台维护。事件来源、场景适用范围、幂等和失效机制也有基础。

DSH 已有固定人格、主对话与后台任务分工、动态背景去重，以及 QQ 自发输出发送链路。应保持这些边界，把缺失信息接通。

### 3.2 需要优先处理的具体问题

以下来自当前本机代码阅读与临时根定向复现，路径均相对 companion-memory；DSH 路径另行标明。

| 环节 | 当前行为与问题 | 对养成与陪伴的影响 | 推荐修正 |
|---|---|---|---|
| 事实来源 | extraction 中相同文本通常直接跳过；跨两次交流的同一事实只保留首次来源 | 真实重复支持丢失，删除影响分析不完整 | 合并独立来源；保留每条来源的时间、episode 和证据类型 |
| 上下文依据 | 用于消解指代的上下文来源并入 source_event_keys | 背景被当成支持，证据数量虚高 | evidence_refs 与 context_refs 分开 |
| 相对时间 | _fact_row 使用处理时钟解析 event_when | 队列隔天处理会把“明天”推迟一天 | 使用每条原始消息 occurred_at 与时区 |
| 反思触发 | 累积至少 5 条未吸收事实，按重要性取最多 20 条；提示要求尽量给出认识 | 一次重要反馈进不来，普通信息凑数也会产出反思 | 按主题、重要反馈与经历终态触发；允许无结论 |
| 反思归并 | 缺少充分的旧认识对照，成长主要按规范化文本匹配 | 同义认识分裂，反证难以改变旧结论 | 支持补充、收窄、推翻、拆分与无变化 |
| 成长计数 | source_event_keys 数量会作为支持，并初始化 actual_result 类型 | 同一经历拆成 5 条信息可能被算成 5 份有效经历 | 按独立经历计数；明确区分陈述、行为、结果与反馈 |
| 演化输入 | composition 的证据适配读取字段与生成反思字段不完全一致，且丢失部分范围和成熟度信息 | 反思依据可能为空，演化范围失真 | 统一证据 DTO，携带 source_fact_ids、来源、范围和资格 |
| 演化筛选 | scheduler 可接收事实和未成熟认识，主要排除删除、终态等情况 | 事实绕过反思成熟条件直接影响人格 | 自动演化限定为符合资格的行为策略或认识 |
| 明确教导 | DSH 的〈改写〉调用事实更正，尚无持久风格教导入口 | “说话太人机”可能只成为一条抱怨记忆 | 增加独立教导链路，直接发布表达规则 |
| 召回输入 | DSH 请求主要只有当前文字与 scope，服务缺少稳定的近期主题补全 | “那个”“后来呢”“拿铁”难以找到背景 | 带来源提供近期主题、事项与受限查询扩展 |
| 消费输出 | DSH renderIncrement 主要消费更正、召回文本和 recent；state / episode / growth 尚未完整进入 | 核心即使有成长，也难以影响 QQ 回复 | 统一渲染有依据的状态、经历、规则与成长 |
| 当前状态 | turn_context 的 companion_state 仍有空占位返回 | 关心中的事与当前回应约束缺位 | 接真实 state 快照，读取与生成同一版本 |
| 完整对话 | bridge 能发送任务/咒语后续正文，但记忆侧仍缺完整独立输出提交 | 用户回应的前一句可能在记忆里缺失 | 补 assistant output 记录、因果关联与发送回执 |

定向复现中的典型样本：两次说“喜欢乌龙茶”没有合并第二来源；同一经历的 5 条普通事实能形成足够支持的成长候选；旧会话有近期背景而新会话为空；“喝咖啡会胃疼”对“想点杯拿铁”的召回不足；只含 state / episode / growth 的返回未生成 DSH 背景。它们分别对应来源合并、独立证据、跨会话工作摘要、语义关联和消费链路的验收。

## 4. 总体架构：四条主链，加一条明确教导入口

~~~mermaid
flowchart TD
    U[用户与助手对话 / 实际工具结果] --> E[原始事件与共同经历]
    E --> F[事实与当前状态]
    F --> R[按主题更新的反思]
    E --> R
    R --> G[有条件的相处策略与成长]
    G --> P[人格局部修订与版本发布]
    T[用户明确教导 / 授权学习示例] --> D[可执行规则与示例]
    D --> P
    Q[新一轮对话] --> C[固定规则 + 工作摘要 + 相关召回]
    F --> C
    E --> C
    R --> C
    P --> C
    C --> A[表达 / 行动 / 合适的主动交流]
    A --> E
    A --> B[真实反馈与结果]
    B --> R
~~~

四条主链回答用户指定的四个问题：

| 主链 | 产物 | 核心原则 |
|---|---|---|
| 对话 → 事实提取 | 当前事实、历史状态、事件引用 | 有上下文、辨主体、保留时间与来源 |
| 事实 → 反思 | 可修订的认识、条件化相处策略 | 新旧对照、允许空结果、处理反证 |
| 反思 → 人格演化 | 局部习惯变化、稳定兴趣与相处方式 | 区分用户模型与角色人格，具备依据和撤回 |
| 对话 → 记忆召回 | 当前有用的上下文与行动依据 | 分层常驻、主题展开、混合检索、预算裁剪 |

“你以后这样说”“学一下这个 bot 的接话方式”是用户直接授予的修改意图，采用专门的快速入口。自动成长的多证据阈值适用于系统自行归纳的结论。

## 5. 记忆对象如何分层

这些是逻辑对象与投影视图，优先扩展现有存储，不要求每层建立一套数据库。

| 层 | 保存什么 | 更新方式 | 进入模型的方式 |
|---|---|---|---|
| 核心身份 | 名字、身份、基本性格、角色背景 | 用户编辑；默认冻结自动改动 | 人格固定前缀 |
| 明确相处规则 | 用户持久教导、称呼约定、回复风格、已授权示例 | 一次明确教导即可形成局部修订 | 紧凑常驻；条件规则按场景选择 |
| 成长与关系摘要 | 相处中已经形成的变化、共同梗、重要关系节点 | 从证据与当前规则后台重建 | 短工作摘要 |
| 重要事实摘要 | 对当前交流经常有用的用户信息与约束 | 事实变更、更正、删除后刷新 | 短工作摘要，范围过滤 |
| 未完话题 | 正在做的事、约定、进展、后续时间和禁提设置 | 明确进展、结果或用户意图 | 当前相关事项；主动候选依据 |
| 事实与经历库 | 原话、双方行为、实际结果、事件时间、来源 | 事件提交、抽取与经历整理 | 按需召回 |
| 反思与成长库 | 有条件的认识、支持与反证、试用和稳定状态 | 按主题归并与反馈更新 | 相关策略优先，深层依据按需 |
| 短期回应状态 | 这次只倾听、当前很累、暂不建议等 | 明确表达；到期或话题结束 | 动态上下文 |

三个工作摘要借鉴 Kindroid 的组织方式；它们都应能从权威记录重建，来源失效时同步重建。不要让摘要成为无法更正的第二事实源。

人格卡保留简明、稳定的角色描述。大量条件、事实和历史放在相应记忆对象中，避免长期把每次经历追加成人格正文。

## 6. 对话 → 事实：先分清发生了什么，再抽取可用认识

### 6.1 同一段对话要产生不同类型的信息

例如：

> 用户：今天答辩完了，你昨天让我别背全文，今天真的顺了很多。
>
> 助手：那昨天那通临时排练还挺值。今晚总算能歇会儿了。

这段可以留下：

- 事件：答辩完成；时间锚点来自用户这条原话。
- 共同经历：昨天排练、今天反馈，属于同一事项中的两个阶段。
- 明确反馈：用户认为“避免背全文”的建议有帮助。
- 反思候选：在这类准备场景中，模拟演练可能更适合用户。
- 助手表达：这次如何回应、是否形成新约定。
- 短期状态：一个事项结束，可以自然庆祝并停止原先的催促。

单次结果可以形成一次有效经历。是否成为普遍的相处策略，还要看适用范围与后续反馈。

### 6.2 最小来源合同

建议在现有记录中补齐下列语义字段，字段可映射到已有合同，避免建立重复来源系统：

~~~json
{
  "subject": "master",
  "applies_to": "shared",
  "episode_id": "episode_defense",
  "evidence_refs": [
    {
      "source_key": "host:rin:private:event_102",
      "kind": "explicit_feedback",
      "occurred_at": "2026-10-27T20:00:00+08:00",
      "quote": "今天真的顺了很多"
    }
  ],
  "context_refs": ["host:rin:private:event_098"],
  "valid_from": "2026-10-27T20:00:00+08:00",
  "valid_to": null,
  "recorded_at": "2026-10-27T20:00:05+08:00"
}
~~~

证据类型至少区分 user_assertion、explicit_feedback、observed_action、tool_result、agent_expression、quoted_example。context_refs 用于理解和追溯依赖，不增加独立支持数量；引用内容应只保留必要片段并参与删除清理。

“助手说完成了”属于 agent_expression；实际工具结果属于 tool_result。收到用户转述的结果时，保留 user_assertion / explicit_feedback 的来源身份，不替换成程序执行回执。

### 6.3 窗口、指代和主体

- 提炼窗口包含角色标记、时间、当前事项和必要前文。前文帮助理解“换大点的”，结论必须落到明确对象。
- 区分说话者、被描述者、第三方引用、假设与角色扮演。别人 bot 的话不自动成为用户事实。
- 稳定偏好、当前计划、已发生事件、表达教导分开处理。“这次用大图”只改变当前任务；“以后展示都大一点”可以形成持久偏好。
- event_when 可空；相对时间按对应原话发生时间解析。多个日期混在同一批次时逐条计算。
- 抽取结果允许为空；临时命令、随口假设和重复镜像不会因出现频率高而变成长期事实。

### 6.4 重复、变化与删除

同一事实再次得到用户支持时，合并真实来源与最近确认时间；传输重试、转发镜像和同一段摘要不增加支持。

“以前喜欢 X，现在喜欢 Y”保留变化历史，当前视图选择有效的新认识。“今天不想喝 X”优先作为临时状态。更新需匹配主体、属性、适用场景和时间范围，不能凭文本相似批量替换。

删除依次影响原文、事实、经历、反思、规则、工作摘要、缓存和在途后台任务；继续复用现有屏障与派生失效机制。

## 7. 事实 → 反思：维护认识，而非按数量生产金句

### 7.1 反思触发

优先由以下变化触发后台任务：

- 用户明确评价了一次互动或结果。
- 一个有意义的事项完成、失败、取消或发生转折。
- 同主题出现新的独立经历。
- 新信息与已有认识冲突。
- 当前认识需要根据新证据更新，或其来源被删除。

普通事实先归入主题，按批次整理。用户明确教导直接走第 8 节，避免等待事实数量阈值。

### 7.2 合成时同时看旧认识与新证据

输入包括当前主题、适用范围、相关旧认识、有效支持与反证、新增原始片段、已采用策略和真实反馈。输出为局部操作：

| 操作 | 使用情形 |
|---|---|
| add | 确实出现一个新的有用认识 |
| reinforce | 同一认识新增独立支持，文本无需扩写 |
| refine | 补条件或收窄适用范围 |
| supersede / contradict | 旧认识已变化，或有明确相反证据 |
| split | 一条过于宽泛的认识需按场景拆开 |
| no_change | 本批没有足够新信息 |

采用按主题的稳定键和受范围约束的语义候选匹配，程序复核来源与操作。文本哈希仍用于精确幂等；不能承担全部同义归并。

### 7.3 反思应写成条件化策略

差的结论：“用户需要陪伴，我要更温柔。”

更可执行的结论：“用户在倾诉工作挫败、尚未提出解决请求时，先接住具体感受，少做条目分析；用户开始询问怎么办后再给一个可行动建议。”

保留触发条件、推荐行为、例外、来源和反馈。这样既容易采用，也容易通过一次反例收窄适用范围。

### 7.4 独立证据怎么算

- 同一次对话拆出的 5 条事实，属于同一经历中的多个片段。
- 同一原话进入事实、摘要、反思、人格提案，仍然只有原始那份支持。
- 不同日期的两次独立互动可以形成两份经历支持；跨天仍在转述同一事件时保持同一因果来源。
- 模型生成的反思是派生认识，不能再次作为原始独立支持。
- 生成、送达、采用、执行结果、用户反馈分别记录。用户沉默、时间流逝、机器人重复强调不增加支持。
- 来源删除或反证出现后重新计算资格，已发布影响沿来源链撤回或重建。

证据量、明确性、适用范围和反证共同决定成熟度。固定“出现两次就永久改变”只适合非常粗的调度门槛。

## 8. 明确教导与模仿学习：单次对话可以直接采用

**可以。用户明确要求改变长期说话或相处方式时，这一轮就建立持久规则，并让接下来的回复采用。** 后台自动成长关闭时，用户主动教导仍可用。

### 8.1 按意图确定影响范围

| 用户表达 | 推荐处理 |
|---|---|
| “以后别每次都总结，像朋友一样接着聊” | 持久风格教导，形成规则并发布 |
| “你说话太人机了，要改” | 结合刚才的具体回复，先修正可辨认的问题，形成可追溯规则 |
| “这次简短一点” | 当前回复约束，结束后不自动转成长期规则 |
| “你看这个 bot 的接话，我希望你学这种感觉” | 授权学习示例，提取节奏、语气和行为方式 |
| “这个 bot 挺好玩” | 普通评价，保留兴趣线索，不自动全面模仿 |
| “可以更黏人一点，但我忙时别追问” | 关系偏好与条件规则，忙碌场景优先 |
| “我开玩笑的，刚才那条别学” | 撤销对应教导及其派生规则 |

“太人机”应优先结合被评价的原回复，识别机械复述、无请求的条目分析、每轮追问、固定关怀句等具体问题。缺乏示例时先采用最小、可执行的改善；需要区分关键方向时在自然对话中简短澄清。

### 8.2 保存规则和示例，而非保存一句抱怨

示意的教导结果：

~~~yaml
kind: explicit_teaching
target: interaction_style
scope: private_shared
intent: persistent
rules:
  - 日常聊天用自然短段，先回应用户刚说的具体内容。
  - 按话题需要决定是否追问，允许自然结束一句。
  - 用户没有请求分析时，少用条目总结和结论式收尾。
preferred_examples:
  - 用户说终于下班时，接住这一天的具体经历和轻松感。
source_refs:
  - 用户评价消息
  - 被评价的助手回复
status: active
~~~

这些规则是针对表达行为的描述，生成时仍保留角色自己的用词和性格。不要把示例固定成每次复读的标准句。

### 8.3 学习另一个 bot 时拆成四部分

1. 原始示例：引用来源、用户选中的片段、完整语境中的必要部分。
2. 学习目标：例如先接情绪、自然接梗、少解释、长短变化、合适的主动分享。
3. 可执行规则：明确场景、行为与例外。
4. 角色内改写示例：用自己的身份和词汇表达同样的互动方式。

示例中的名字、人生经历、承诺、关系和声称做过的事情保留为引用素材。进入自身记忆的应是用户授权学习的表达机制；共同经历仍来自真实相处事件。

### 8.4 处理与发布顺序

1. 确认来源是有权限的真实用户消息，关联被评价回复或示例。
2. 从当前对话识别持久／临时意图、修改目标与范围。
3. 生成少量局部规则，检查与当前规则和身份段的冲突。
4. 原子保存教导记录、局部 revision 与待发布任务；使用现有版本比较机制处理并发。
5. 发布新的规则／人格版本，在下一次模型生成边界采用；本轮尚未开始生成时即可采用。
6. 显示采用结果，并记录后续自然反馈。已经明确要求修改时，无需再让用户审批同一意图。

短时服务失败时，当前回复仍遵守对话中的用户指令；持久保存进入有幂等键的重试队列。管理面显示待保存状态，对话避免宣称已永久保存。已有持久任务继续恢复，不能因重启丢失这次教导。

### 8.5 接口与权限建议

建议新增 POST /v1/persona/teach，由已有用户消息或已保存事件引用提交，服务端读取原文并判定目标。请求包含来源、当前版本、可选示例来源和预期 scope，返回 teaching_id、revision、published_version、status。

这是拟新增合同。DSH 现有〈改写〉仍负责事实更正；风格教导使用独立动作。客户端只获得明确范围的教导能力，无需授予完整人格管理权限。群聊中普通成员或被引用的 bot 文本不会因为被模型看到就取得全局改卡权限。

相同范围内，后来的明确教导可以替换旧规则并保留历史；当前具体请求在当前场景优先。核心身份按现有冻结和用户编辑权限处理，局部风格指令只修改对应部分。

## 9. 反思 → 人格演化：分开“了解你”“了解我们”“改变自己”

### 9.1 三类认识分别落位

| 新认识 | 应写入 | 示例 |
|---|---|---|
| 关于用户 | 用户模型／事实／偏好 | 用户忙时偏好短消息 |
| 关于双方 | 关系记忆／互动策略／共同约定 | 用户用某个昵称表达亲近；争执后希望先讲清具体误会 |
| 关于角色自身 | 可演化习惯、兴趣与人格局部段落 | 经多次共同探索后形成某项稳定兴趣与自己的表达偏好 |

“用户喜欢摄影”首先改变对用户的理解。共同摄影经历、角色自己的选择与稳定反馈，才进一步支持“角色也逐渐喜欢讨论摄影”。

关系不压缩为单一亲密度。采用可解释的维度：熟悉的称呼、共同梗、信任约定、协作习惯、敏感话题边界、修复过的分歧和共同里程碑。

### 9.2 三种变化速度

| 路径 | 何时采用 | 采用形式 |
|---|---|---|
| 用户明确教导 | 单次明确指令即可 | 直接局部修订和发布 |
| 自主形成的低影响策略 | 有明确场景与有效经历后，可先试用 | 可撤回的条件策略；观察后续自然反馈 |
| 稳定习惯、兴趣与深层人格变化 | 多次独立经历、时间跨度与一致反馈支持 | 整合进相应人格段落，保留来源与旧版本 |

明确教导无需等待自主成长成熟。自主学习也不需要把所有微小改善都等到长周期后：先用条件策略解决当前相处问题，稳定后再简化为人格习惯。

### 9.3 自动演化输入必须具备资格

自动演化候选携带：目标层、适用范围、支持与反证、独立经历数、采用反馈、成熟状态、来源版本及删除版本。原始事实供模型解释依据，不直接获得改人格资格。

2026-10-27 资格定案：裸反思必须处于 confirmed / promoted 状态、有至少两份独立经历，并至少含一类有效交互证据（user_feedback、actual_result、both_party、real_contact）。用户反馈可以单独满足交互条件，工具执行结果并非必需；只有纯陈述的反思保留用于理解与召回，不自动获得改卡资格。来源删除后按剩余依据重算。明确教导不经过此门槛。

修复当前证据适配器字段不一致，统一 reflection → evidence → evolution 的合同；scheduler 只选择符合资格的候选。冻结身份、场景隔离、局部 diff、发布、回滚与删除联动继续复用。

当模型建议将某条认识写入人格时，先检查它是否更适合留在用户模型、关系规则或当前状态。真正写卡的内容保持短、稳定、可辨认。

### 9.4 让成长被用户感知

通过行动呈现变化：接话方式变了、记得某个约定、主动带来一件相关发现、共同梗在合适的时刻出现。管理台可以展示“因为什么改变、现在怎样做”，日常对话无需反复播报“我正在成长”。

角色的好奇心和偏好可以带来适度的主动性：对共同话题提出自己的看法、选择相关资料、提议一个小目标。实际离线活动、阅读或工具行动要有对应事件结果；表达兴趣与声称做过某件事分别记录。

## 10. 对话 → 召回：比单纯向量更适合本项目的方案

**推荐“紧凑常驻规则 + 当前工作摘要 + 多路候选召回 + 有依据的排序”。** 向量是其中一路，对“拿铁／咖啡”“答辩／上次排练”等语义关联有帮助；时间、事项状态、称呼和明确禁提由结构化条件处理。

### 10.1 三层输入

| 层 | 内容 | 选择方式 |
|---|---|---|
| 每轮必要 | 核心人格、有效持久教导、当前明确约束 | 紧凑固定块；版本变更时更新 |
| 当前工作摘要 | 成长与关系、重要事实、未完话题中的相关片段 | 按角色、用户、场景与当前主题选择 |
| 按需长期记忆 | 历史事实、具体经历、相关反思和来源 | 多路召回、去重、重排、预算裁剪 |

近期原始对话继续承担准确接话；跨会话工作摘要提供连续性，避免直接把别的会话全文混进当前消息历史。

### 10.2 检索流程

1. 从当前文字、近期真实对话、正在延续的事项中构造查询。短句可以补主题，明确新话题时停止继承旧主题。
2. 先执行主体、场景、删除更正、有效时间和提及限制过滤。
3. 并行获取关键词 BM25、语义向量、实体别名、时间窗口与 episode / thread 邻接候选。
4. 使用现有 RRF 融合，补充证据质量、当前有效性和话题连续性判断；去除同源重复。
5. 对少量高歧义候选按需要重排；没有独立收益样本时先使用确定性排序。
6. 按预算输出可用内容及来源。必要时展开同一经历的少量相邻节点。
7. 生成前复核版本；消费后记录实际使用、提及和反馈。

Hindsight 的多路融合可作为结构参考：[retrieval](https://hindsight.vectorize.io/developer/retrieval)。Zep 的时间视图帮助区分历史与当前：[facts](https://help.getzep.com/facts)。

### 10.3 当前阶段的检索选型

先完成 MC02-A：近期主题、短句指代、跨会话摘要、实体别名、事项与经历展开，以及 DSH 的真实消费。随后用已有 EmbeddingProvider 端口接 MC02-B，对语义关联样本进行比较。

小规模数据用现有 SQLite/FTS 和本地关联表即可；向量存储按实际规模选择现有持久化扩展。增加付费接口、账号或新模型运行环境时，先明确其条件。

大模型更适合做受限查询展开、归并与少量重排。每轮遍历全部历史再让模型筛选，会增加延迟、成本与来源控制难度。

### 10.4 避免检索破坏自然聊天

- 召回只提供当前有用的信息；不要求每轮主动提起旧事。
- 用户说“今天想喝拿铁”，咖啡相关约束可以帮助回应，但是否提醒仍看用户当下语气和明确边界。
- “后来怎么样”优先续接最近一个未完事项；多个事项同样合理时自然澄清。
- 旧反思与新事实冲突时采用当前事实，并安排后台修正旧反思。
- “别再提”保留提及限制；“忘掉”进入真实删除，两者分别处理。
- 固定提示与已提交历史保持稳定，动态背景增量追加并去重；历史压缩后按代次重建注入集合。
- 向量索引、工作摘要和关系投影均遵守源数据删除与失效，重建索引也经过屏障。

## 11. 共同经历、未完话题与主动交流

### 11.1 一个经历保留哪些内容

最小 episode 包含参与者、原始时间、起因、关键互动、实际行动、结果、用户反馈、相关约定和终态。thread 可以跨多个 episode，负责一件持续的事。

例如“准备面试”可以串联：确定日期 → 一起整理问题 → 模拟回答 → 面试完成 → 用户反馈。每一步记录来源和时间，后续可根据“面试结果”召回到之前的准备过程。

重试、镜像转发和摘要沿用原始因果身份。不同客户端会话并不自动代表不同经历。

### 11.2 未完话题怎样收尾

状态复用现有 companion_state：open、waiting、done、cancelled 等可映射到已有字段。下一次跟进时间、是否允许主动提及、用户最近反馈另行保存。

“先不聊”停止当下延伸；“不要再提”加提及限制；“事情结束了”更新终态。时间流逝与用户没回复不会自动宣告完成，也不会增加亲近程度。

### 11.3 主动消息从真实缘由产生

优先来源：

- 一个用户在意的事项到了适合跟进的时间。
- 双方约定了提醒、回访或分享。
- 真实任务有新结果。
- 实际获得的新信息与近期持续兴趣有关。
- 一段共同经历产生了有依据、适合分享的新发现。

每个候选携带来源、理由、有效时间、冷却和提及限制。调度检查静默时间、用户是否刚发言、近期是否已跟进同一事项；相关结果出现时唤醒，日常候选在合适时机合并处理。

普通主动消息可先试用每日最多 2 次、间隔至少 90 分钟、用户时区 00:00—09:00 静默，再按实际接受度调整。这是初始试用参数；明确约定的提醒遵循约定时间。

2026-10-27 时机定案：普通未完事项的初始跟进间隔保留 thread_followup_min_hours=12；现有每日上限、间隔、同题冷却和静默窗保持，不新增发送门禁。12 小时决定何时产生跟进候选，发送前仍检查最新语境；具体打扰样本先检查来源、终态和内容质量，再决定是否调为 24—48 小时。

用户抢先发言时，重新判断候选是否仍需要单独发送。发送分段失败只重试未送达部分。正文、输出 ID、原因和送达回执进入统一经历链，之后用户的“嗯后来呢”才有可接续的前文。

### 11.4 自然感的具体标准

一次有具体缘由的简短跟进，往往比固定“早安晚安＋记得喝水”更有价值。允许消息只是分享、感想或接梗，避免每次用问号索取回应。

用户未回应时按冷却处理；反馈明确表示打扰时调整对应触发条件和频率。陪伴感同时包含及时出现与尊重节奏。

## 12. 服务、后台与多端一致性

### 12.1 快慢任务分工

| 时间位置 | 必要工作 |
|---|---|
| 当前轮生成前 | 当前明确指令、已发布规则、相关工作摘要与召回，固定依据快照 |
| 用户明确教导时 | 小范围教导理解、幂等保存、局部修订和发布 |
| 普通轮提交后 | 事实／状态／反馈候选提取，合并已有批次 |
| 有意义事件发生后 | episode 更新、同主题反思、摘要刷新 |
| 后台维护 | 重试、索引与摘要重建、合格成长提案、主动候选维护 |

借鉴 Letta 的后台 consolidation，把耗时整理放入已有 maintenance / outbox。明确教导具备优先级；普通聊天不默认串行调用多个模型进行抽取、反思、评判和人格演化。

### 12.2 一份权威状态

记忆核心是权威写者，DSH、QQ bridge 和 N.E.K.O 消费固定快照与发布版本。缓存只用于读取和待同步，不各自生成一套永久人格与事实库。

拟新增或补齐的合同：

| 合同 | 用途 | 与现有接口的关系 |
|---|---|---|
| POST /v1/persona/teach | 明确教导、授权示例与撤销关联 | 新增受限能力，复用修订和发布 |
| POST /v1/outputs | 助手自发／任务反馈正文及因果来源 | 沿用连续性方案；避免冒充用户事件 |
| /v1/receipts 的输出分类 | 输出采用与实际送达的区分 | 扩展现有回执合同 |
| /v1/context 增补输入输出 | 近期主题、当前事项、规则、经历、state / growth | 扩展现有端点并接通真实渲染 |

接口名称是实施建议，落地时先核对当前路由与合同。角色、scope、来源、请求幂等和版本校验都在核心边界完成。

### 12.3 必须一起处理的失败行为

- 用户重复提交教导：按同一来源幂等，避免多次加权和重复 revision。
- 并发改卡：比较 base_revision；冲突后重新基于当前规则生成局部修改，不覆盖其他编辑。
- 已删除来源的晚到反思或教导：拒绝提交，取消对应派生影响。
- 召回期间来源或版本改变：复核并重建必要上下文。
- 摘要刷新失败：保留上一份仍有效快照；失效部分立即过滤，并保留重建任务。
- 生成成功但 QQ 送达失败：保存生成记录与待送达状态；实际送达后再更新回执。
- 重启恢复：沿用 journal / outbox 重放，不把持久请求重新解释成新的经历。
- 自动成长关闭：停止系统自行提案与采用；用户主动编辑、明确教导与事实更正保持可用。

### 14.2 质量观察

| 维度 | 观察方式 |
|---|---|
| 教导采用 | 明确教导后第一次、跨天、重启后的回复是否体现规则；纠正后是否反复犯同类问题 |
| 相处策略 | 同一策略在适用场景帮助交流，在例外场景及时让位 |
| 连续性 | 跨天接上事项、知道进展与终态，能正确区分两件相似的事 |
| 自然度 | 机械复述、无请求分析、固定收尾、每轮追问和突兀翻旧事的比例 |
| 自主性 | 有来源地分享、选择、接梗与跟进，表达有变化并保持角色身份 |
| 成长质量 | 每个变化可追到经历或明确教导；反证能改变它；删除能撤回影响 |
| 主动接受度 | 打扰反馈、同一事项重复跟进、无回应后的频率变化 |
| 正确性与成本 | 时间、范围、删除、来源完整率；召回延迟、前台模型次数、上下文体积 |

用同一组中文对话样本比较改动前后，再做跨天真实交流。重点记录用户哪里需要重复解释、哪里觉得突兀、哪里感觉“她学会了”。真实反馈优先于模型自评分。

## 15. 本次设计确定的决策

1. 保留现有核心和单写者机制，在本机完成开发与验收，使用 Git 加版本包同步。
2. 明确教导和授权示例拥有快速路径；用户自主编辑不受自动成长开关限制。
3. 自动反思维护已有认识，允许空结果；自主成长按独立经历与真实反馈形成。
4. 区分用户模型、关系模型和角色人格；稳定身份、条件习惯与短期状态分别管理。
5. 增加成长与关系、重要事实、未完话题三个可重建工作摘要。
6. 保留共同经历中的双方行为、实际结果和约定，连接主动交流与后续回应。
7. 采用分层混合召回，优先补齐主题、时间、事项和消费链路，向量随后补语义关联。
8. 第一项最直接的体验交付是明确教导后下一轮改变；整体验收看跨天连续性和长期行为。
