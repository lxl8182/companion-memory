3. **明确的对话接口**：S04 已区分服务生成回复、接收外部已完成的对话、只读取上下文；主体/场景透传和生成时的记忆接线需按 R03/R05 补齐。

## 2. 运行所有权与新系统启动

### 2.1 独立服务是唯一日常运行方式

同一数据根同一时刻只有一个写入进程；角色之间的内部调度仍可分别进行。按用户 2026-10-24 的决定，S05 完成后不再提供内嵌模式选择，旧配置与旧启动路径退役。

| 模式 | 核心、屏障与维护循环的所有者 | N.E.K.O | WebUI |
|---|---|---|---|
| 独立服务 | rin-memory 服务进程 | HTTP 适配器转发记忆请求 | 经独立服务 API 读写 |

管理台由权威进程同源提供静态页面和 API。在线管理台不再建立第二份 `MemoryCore` 或直接读写 JSON；离线开发工具可使用任意数据根。

独立服务不可用时，客户端返回可重试错误或按已定义的可选召回规则降级，不自动启动本地写者，也不转回旧记忆写入路径。已收到的待上传轮次保留稳定标识；已有持久重发机制继续复用，没有该机制的客户端显示“待同步”，不能显示为已保存。

### 2.2 所有写入口执行同一锁协议

S01 已统一使用**规范化数据根的进程所有权锁**。新运行链路沿用该实现：

- 独立服务及显式离线写工具均在装配可写核心前取得同一根锁；宿主和在线 WebUI 通过 API 写入。
- 数据根按真实路径识别，处理 Windows 大小写和目录别名，避免同一目录获得两把互不关联的锁。
- 优先使用进程存活期间持有的操作系统文件锁；PID、时间与模式用于说明冲突，不能代替互斥。
- 现有“内容不可读即清理旧锁”的行为需要修正：另一进程刚创建但尚未写完的锁文件不能被当成废弃锁删除。
- 角色内的提交、删除、维护仍使用现有锁和写许可。根锁解决跨进程所有权，内部事务解决同进程并发。
- 所有写任务和底层 I/O 结束后才释放所有权；异常退出后由锁机制解除占用。
- 服务写入新数据根并执行自身写许可；新链路不接管旧 N.E.K.O 数据或依赖旧存储迁移/云存档许可。

验收覆盖“服务＋服务”“服务＋离线写工具”、同时争抢、异常退出再启动和路径别名；同时检查宿主和 WebUI 均未创建本地核心。第二个写者应在任何数据修改前被拒绝。

> **S01 已实现（2026-10-23）**：`persistence/ownership.py` 提供 `canonical_root` + `acquire_root_lock` + `read_root_lock`，锁文件为 `<root>/.rin_memory.root.lock`。已接入 CLI `run`/`migrate`/`rollback`、宿主 `engine_bridge/runtime.py`、WebUI 可写在线模式；只读入口不取锁。实现要点与上面的要求一一对应：规范化真实路径（大小写/`.`/`..`/尾分隔符/目录别名同一把锁）；互斥来自 OS 文件锁，`pid`/`mode` 写入锁记录仅用于排障；**不再有「内容不可读即清理旧锁」**——原实现的 `O_CREAT|O_EXCL` 建文件后才写 pid 存在真实竞态，已改为先取锁再写记录；锁记录位于锁定字节之前，因此持锁期间其他进程仍可读到持有者。进程异常退出由 OS 自动释放，重启无需清理。
>
> S04 已将独立 HTTP 服务接入同一根锁；退出时的在途工作与锁释放按 R02 验收。上述 S01 记录保留历史接入成果，S05 运行入口以独立服务为准。公网/多机场景另行设计。

### 2.3 从空目录初始化与启用

1. 新入口生成 `stack.toml` 与独立运行目录，显式配置服务、宿主、模型和资源。
2. 服务取得新记忆根所有权并开放管理台；空库通过页面新建角色、初始人格并发布。
3. 宿主从新配置连接服务，管理台同源访问同一实例；所有新记录与待同步队列写入新根。
4. 按 S05 的 N01—N15 验收新系统，包括新数据的重启恢复、删除一致性和实际表现链路。
5. 验收通过后退役旧配置读取、旧启动入口及内嵌核心路径，日常入口统一到新启动器。

旧数据迁移、旧基线比较、内嵌模式回退和旧目录清理不进入本轮实施。开发与验收细节以 [S05 新系统计划](s05-new-system-plan.md) 为准。

生产入口只使用新配置指定的数据根，校验目录与格式；不通过旧锚点或旧配置猜测路径。所有入口（服务、宿主、管理台、离线演练工具）都可直接使用现有运行根与 `nekodata`；测试数据不必保留，人格卡不重建。

## 3. 接口与整轮提交

### 3.1 最小接口集合

以下为首版拟定的服务接口。现有宿主 HTTP 路径由适配器转发并保持原响应合同；管理台复用已有读写能力。

| 接口 | 用途 | 生成与写入责任 |
|---|---|---|
| `POST /v1/chat` | 输入用户文本，由服务取上下文并生成回复 | 服务生成并提交整轮 |
| `POST /v1/turns` | 上传客户端已经生成的一轮对话 | 服务保存与入队，不再次生成 |
| `POST /v1/context` | 读取人格、近期会话和相关记忆 | 不调用对话模型、不记录为已提及或已送达 |
| `GET /v1/requests/{request_id}` | 查询提交进度或取回已提交结果 | 受角色、主体和删除约束 |
| 现有管理 API | 查询、更正、删除、人格编辑/发布、演化与状态 | 委托同一核心，保留版本冲突与回执语义 |

一次业务轮次只能有一个生成方。使用 `/chat` 的客户端不再把其回复当作新的 `/turns` 上传；外部生成模式先取 `/context`，生成后提交 `/turns`。相同轮次的镜像仍引用原来源，不能算作新经历。

N.E.K.O 首先使用“外部生成＋上下文读取＋整轮上传”，保留现有语音、情绪、Live2D、打断及工具调用链路。

> **S04 接口主体已实现（2026-10-24）**：四个端点与 `/v1/health` 均在 `service/server.py` 的 `MemoryApi` 中，传输为标准库 HTTP（默认仅回环、校验 Host/Origin、统一错误信封）。`/context` 只读（测试断言不产生 turns/recent/facts）；`/turns` 在无模型配置时依然可用。`context_receipt_id` 当前由 `persona_version + card_revision` 派生，过期引用检查待补；范围透传、实际生成上下文、错误恢复与退出并发等问题按 §8.1 修复。流式 `/chat` 另行评估。

### 3.2 请求与响应合同

公共请求与回执使用明确的 API 版本。首版字段如下，按入口需要取用：

| 字段 | 约定 |
|---|---|
| `client_id` | 服务配置识别的接入方；用于权限和排障，不用于拆分同一经历 |
| `character`、`subject` | 必填身份边界；先校验权限再读写，不从显示昵称推断主体 |
| `session_id`、`turn_id` | 会话与业务轮次标识；重发保持不变 |
| `parent_turn_id` | 该会话最后已提交轮次；首轮为空，用于检查并发与顺序 |
| `request_id` | 单次业务请求的幂等键；网络重试沿用，不使用重试时刻生成新键 |
| `occurred_at` | 原始发生时间，包含时区，重试保持；服务另记 `received_at` |
| `source_key`、`episode_id` | 适配器复用既有来源键和经历关联规则；镜像引用同源 |
| `scene`、`applies_to` | 发生场景与适用范围分别表达；省略范围时按入口政策处理，不自动扩大共享 |
| `content_class` | 外部事件明确标注；普通聊天入口可由服务补 `chat`，详见 §5.1 |
| `text` / `messages` | `/chat` 接收用户文本；`/turns` 接收有明确说话者的整轮消息 |
| `context_receipt_id` | 使用本服务上下文生成的轮次原样回传，关联人格版本及失效检查；纯外部历史允许省略 |

纯外部历史没有上下文引用时，记录为外部来源，不宣称使用过本服务的人格版本，也不产生 adopted 回执；仍校验身份、来源、范围与删除屏障。

对外消息使用标准 `role/content`。适配器统一转换为当前核心接受的 `type + data.content`，保留说话者、来源和范围元数据；外部输入不能通过角色字段注入系统指令。兼容既有宿主形状的转换留在宿主适配器。

`/context` 返回当前可用的 `persona_version`、`card_revision`、分开的上下文块、召回状态和 `context_receipt_id`。引用绑定角色、主体、会话、数据根代次及相关删除/更正状态；缺失、过期或身份不符时明确报错。临时引用在重启后可要求重新获取，不作为永久事实。

写响应返回 `request_id`、`turn_id`、`status`、`durable`、`replayed`、`processing_position`、`extraction_status`，以及实际生成使用的人格版本；`/chat` 完成后还返回回复。已提交、已提炼、已送达和已采用人格分别表达。

统一错误结构为 `code/message/retryable/request_id`。至少区分：

- 参数或格式错误：400；身份权限错误：401/403；
- 请求正文冲突、轮次顺序冲突、上下文失效：409，失效时带 `needs_reissue`；
- 结果已删除或失效：410，不返回旧回复正文；
- 在途处理中：202，附状态查询位置；容量已满：429，附重试提示；
- 存储未就绪或所需模型不可用：503；本次上游调用超时：504。

同一会话按“角色＋主体＋session”顺序提交。首版同一会话仅允许一个生成/提交请求在途，新轮次返回 `turn_in_progress`；相同请求重试读取其状态。不同会话可并发，但共用有界模型并发和存储事务。

### 3.3 生成与降级顺序

```
校验身份、范围、轮次与幂等键
  → 已提交请求：经当前删除/更正检查后回放原结果
  → 新请求：登记待处理状态，固定本轮输入和发生时间
  → 读取必需人格快照、近期会话和约束
  → 在预算内补充可选召回
  → 生成回复（服务生成模式）
  → 检查上下文是否被删除、更正或数据根切换失效
  → 持久提交整轮内容、生成版本和提炼意图
  → 幂等应用消息视图及提炼队列
  → 返回已提交结果；后台进行提炼
```

`/turns` 跳过取上下文和生成步骤，校验已提交消息及其上下文引用（如有），进入同一持久提交路径。服务生成模式中，人格、角色/主体身份、删除屏障和必需更正约束读取失败时停止本轮。可选召回超时、向量不可用时保留必需内容，返回降级状态；不能把整份上下文一并清空。

生成期间发生普通人格发布，本轮沿用已固定版本，下轮采用新版本。删除、更正或根代次变化使本轮依据失效时，旧结果不提交，返回 `context_stale`；外部客户端重取上下文，以新 `request_id` 重新生成，失败尝试不占用最终业务 `turn_id`。

生成失败或取消时不保存为一轮已完成对话；待处理记录标为失败或中断，并受同一删除及保留策略管理。近期上下文保留完整说话者关系，助手内容只用于会话连续性，不直接作为用户事实证据。

HTTP 返回成功表示结果已提交。实际显示、播放、人格采用和提及反馈继续使用消费者回执；未送达回复不能被当成用户已经知道的内容。回放已提交回复时客户端按 `turn_id` 去重，避免重复展示或播放。

### 3.4 提交、幂等与恢复

现有 `ingest_turn` 先登记来源，再保存 recent/原文并入队。入队失败后重启重试会提前返回 `duplicate`，留下“对话已保存、提炼任务缺失”。服务化必须先补齐这一断点，不能只在 HTTP 层增加去重。

> **S03 已增加 duplicate 补队列分支（2026-10-23）**：`OutboxStore.find_by_source_key` + `ExtractionService._repair_missing_extraction_op`。重试命中 `duplicate` 时，若该来源没有待处理 op 且本轮仍带原文，则补入一次提炼任务；已有 op 时不重复入队。`tests/test_s03_ingest.py` 用固定时钟覆盖该分支。2026-10-24 复核发现真实时钟下重试会先因 `occurred_at` 变化而冲突，进入不了补队列分支；剩余修复归 S02，见 R04。
>
> **S02 已提供请求级台账（2026-10-23；2026-10-24 复核补充）**：`persistence/turns.py` 的 `TurnRequestStore` 持久化 pending/committed/failed/interrupted/deleted 状态，`domain/turns.py` 的 `TurnCommitService` 负责请求提交。整轮记录经 `journal.record_and_save` 提交（事件类型 `core.turn_committed`），「journal 已 fsync、视图未保存」窗口由 `recover()` 回放修复；同键已提交结果可直接回放。S04 已提供 HTTP 层。**仍待补齐**：实际删除/更正到结果清理的接线（R01）、原文保存后入队失败的恢复（R04）、服务生成回复的整轮保存（R05），以及请求结果的保留期策略。

**最小实现**：扩展既有 journal 和恢复处理器，保存一条包含整轮消息、来源、生成版本及提炼意图的提交事件；由它幂等推进 recent、时间索引、outbox 和请求结果。复用现有存储，不引入第二套独立队列。

| 状态 | 含义 | 重试与恢复 |
|---|---|---|
| pending | 请求已登记，生成或提交尚未完成 | 查询返回处理中；重启后区分可恢复提交与中断生成 |
| committed | 整轮和后续工作已持久记录 | 返回同一回复与版本，续完缺失视图和入队步骤 |
| failed / interrupted | 尚无成功提交，可定位失败阶段 | 可重试失败允许沿原请求恢复；修改输入需新请求 |
| deleted / invalidated | 结果或其依赖已被删除、更正失效 | 返回失效状态，清理正文，不回放旧内容 |

实现约束：

- 请求键以“接入方＋角色＋主体＋request_id”定位；业务来源再以稳定 `source_key/turn_id` 去重，覆盖跨客户端镜像。
- 请求指纹覆盖业务输入和范围；忽略接收时间等传输字段。首次发生时间固定，重试不能重新取当前时间改变指纹。同键不同输入返回冲突。
- journal 提交前失败可重试；提交后即使视图或队列未完成，也只能续作，不能重新生成或追加第二轮。入队使用稳定操作标识。
- 只有整轮及提炼意图已持久化才返回 `committed/durable=true`。提炼完成另有状态，不阻塞正常回复。
- 进程在模型返回后、持久提交前退出时，可能需要重做生成；验收约束是最终一轮只提交一次。已经持久提交的回复必须原样回放。
- 删除/更正同时覆盖请求结果、待处理输入、上下文引用、派生缓存及恢复日志中的受影响正文。保留防重放所需的最小标识；日志重放和历史恢复先应用最新屏障。
- 新增回复记录保留生成时的依据关联；依据失效时禁止返回旧回复，清理过程沿用现有删除回执，不把正文留在永久审计记录中。
- 同进程并发的提交、维护和删除也执行统一写许可与失效检查，模型调用在存储临界区外进行。

关键验收：来源登记后失败、原文保存后入队失败、提交后 HTTP 响应丢失、同键并发重试、生成中删除、删除后重启回放，均不产生重复轮次或遗漏后续工作。

## 4. 模型适配与常驻运行

### 4.1 模型适配器

实现现有 `ModelInvoker.invoke(tier, messages, max_output_tokens, timeout_s, purpose)`。消息保持列表形状，返回原始文本，结构化内容由领域层解析；传输、鉴权、限流和格式错误保留可识别原因。

| 档位 | 用途 | 要求 |
|---|---|---|
| summary | 事实抽取、压缩、反思及当前演化模型调用 | 按现有调用点映射；用于后台任务 |
| conversation | 独立 `/chat` 回复 | 启用服务生成时配置 |
| 其他显式档位 | 按实际已配置的能力映射 | 没有调用方的档位不列为必需；不存在的映射明确报错 |

更正接口沿用现有领域能力；只有实际接入语义模型时才新增对应档位。档位可共用同一模型配置，但前台与后台任务使用有界并发，避免后台提炼占满对话容量。

核心继续保持零运行依赖。HTTP 服务和模型适配器使用独立可选依赖组，不把 Web 框架、HTTP 或推理运行时导入核心默认路径。优先使用支持期限、取消和连接复用的异步客户端；已有项目可复用的适配能力优先于新依赖。

如果使用标准库同步 HTTP＋线程池，必须设置底层网络期限和并发上限，并追踪工作线程至结束。取消协程等待不会自动终止正在执行的线程，不能在其仍可能写回时释放所有权。参考 [Python Future 取消语义](https://docs.python.org/3.11/library/concurrent.futures.html#concurrent.futures.Future.cancel)。

密钥由环境或本机受控配置提供，不进入命令行参数、前端响应、普通日志和导出。独立模型适配支持显式代理；访问本机记忆服务不使用外网代理。

### 4.2 启动检查与健康状态

启动时校验数据路径、配置、凭据引用、档位映射和存储格式。配置错误或存储恢复失败阻止相关能力开放；模型探测在有界期限内完成，结果进入能力状态。

```
加载显式配置与路径
  → 取得根所有权锁与写许可
  → 装配核心、注册全部恢复处理器
  → 恢复删除屏障、journal、整轮提交及 outbox
  → 建立就绪状态，启动所需后台任务
  → 开放相应读写和对话能力
```

| 状态 | 判断 | 行为 |
|---|---|---|
| liveness | HTTP 进程能响应 | 轻量检查，不读全库、不调用模型 |
| storage_ready | 锁、写许可、格式与恢复通过 | 决定是否开放记忆读写；写入暂停时显式报告 |
| chat_ready | storage_ready、人格可用、对话模型可调用 | 决定 `/chat` 是否可接收请求 |
| background_ready | 维护任务存活、所需模型可用 | 决定是否运行模型后台步骤；失败可观测 |
| degraded | 可选召回、模型或后台步骤暂时不可用 | 报告具体能力和原因，保留可工作的接口 |

`summary` 不可用时显示提炼暂停并保留任务，仍可查看、更正、删除已有记忆；`conversation` 不可用时拒绝新的 `/chat`，允许外部整轮上传。周期健康检查不发起模型调用，模型状态由启动探测、真实调用和有界重试更新。

### 4.3 后台维护、容量与退出

- 复用已有维护步骤，默认间隔 60 秒，同角色不重叠运行。阻塞恢复、文件和索引 I/O 离开事件循环执行。
- 任务状态至少包含待处理数、最老等待时间、失败次数、死信数、最近成功时间及具体失败步骤。不要只显示进程存在或“十步正常”。
- 限流和网络失败采用有界退避；鉴权、配置错误暂停相应能力，不每轮消耗重试次数。死信可查看原因并显式重试。
- 输入大小、在途请求、模型并发和积压任务有上限。容量不足时在承诺接收前返回 429/503；已持久接收的任务保留并报告状态，不静默丢弃。
- 停止时先拒绝新写请求，再停止领取后台任务；让短提交完成，将未完成生成标为中断，关闭模型客户端，等待底层工作退出，最后关闭存储并释放锁。设置退出期限，超时走进程终止及下次恢复。
- 每轮分别记录上下文构建、模型首字/完整生成、持久提交、队列等待与后台处理耗时。非流式首版测完整生成时间，不把模型耗时归入召回预算。

默认只监听回环地址。可写本机服务也检查 Host/Origin、限制 CORS，管理台使用同源会话或写请求令牌，外部客户端使用独立凭据；日志和公共健康信息不返回原文与密钥。公网监听需要另行设计鉴权、TLS 和部署边界。

### 4.4 安装与首次使用

交付安装包包含实际服务入口、所需静态页面与可选依赖声明；wheel 默认导入核心时不加载服务或模型运行时。离线管理、演练和生产运行命令要有明确区分。

首次运行要求显式新数据目录。新角色通过管理 API 创建初始人格卡并发布；之后重启沿用服务内的当前卡和版本，不从模板覆盖。未初始化人格的角色允许配置和查看状态，`/chat` 返回明确的初始化要求。

独立安装验收从构建后的包启动，不依赖仓库当前目录、N.E.K.O 导入路径或开发环境的隐式依赖。模型和凭据由测试配置注入。

## 5. 内容分类与中文链路

### 5.1 分开处理保存、提炼与适用范围

当前分类器允许 `unclassified` 参与提炼，正常聊天和历史消息也会使用该分类；`ingest_turn` 对不提炼类别还可能提前返回，跳过整轮原文保存。实施时同时修正入口标注和保存流程，避免收紧闸门后正常对话停止记录。

| 输入 | 原文处理 | 事实/成长处理 |
|---|---|---|
| 普通用户聊天 | 保存整轮和说话者，入口补 `chat` | 仅提炼有依据的稳定事实、偏好、约定或未完成计划 |
| 外部完整对话但类型未知 | 可保存会话记录，显示待分类原因 | 默认不提炼、不晋升人格 |
| 游戏流水、工具结果、系统通知 | 按来源政策留在事件记录或原插件，不伪造为用户发言 | 不进入用户稳定事实 |
| 临时战术或本次工作要求 | 随会话保存，保留 game/run/任务范围 | 不扩为通用偏好 |
| 明确长期偏好、生活聊天 | 保存来源和适用范围 | 即使发生在游戏或工作场景也可提炼 |
| 助手回复、自述或镜像 | 保留会话与同源关系 | 不冒充用户陈述，不增加独立支持次数 |

例如“这次用英文写注释”是局部要求，“以后代码注释都用中文”是明确长期偏好；内部兜底不能仅凭“代码”“战斗”等词整体丢弃消息。

可信入口提供的合法标注优先，但不能覆盖说话者、来源权限和明确的工具输出类型。对未知类别和非法标注返回可观察原因，不自动按可提炼聊天处理。

先让普通聊天、游戏生活聊天和外部上传适配器正确携带分类，再收紧未知外部输入。历史 `unclassified` 沿用已有时间屏障及兼容策略，不因新默认值批量重提炼或改写旧事实。

验收覆盖稳定生活事实、工作长期偏好、临时工作要求、游戏流水、工具结果、未知外部事件和混合消息。分别断言原文去向、提炼结果、主体与适用范围，不以“所有工作指令零事实”作为标准。

### 5.2 中文编码的定位与修复

**S03 定位结论（2026-10-24，已按本节四步顺序完成）**：核心链路**逐层字节保真**，损坏不在核心存储层。样本 `她喜欢乌龙茶🥤，说“下次再聊”——记得提醒我！` 在九个层次上逐字符一致：输入 dict → `message_text` → `ingest_turn` → `recent.json` 磁盘字节（无 `\u` 转义）→ `time_indexed_original` 行 → 送入模型的 prompt → 模型回写事实 → `facts.json` 字节。宿主 `_to_core_message` 的四种输入形态（langchain、cross_server role、多模态 list、字符串 list）同样保真。用 `PYTHONIOENCODING=cp1252` 起子进程验证过：控制台编码不足只影响**打印**，不影响落盘内容。

因此排查后续只需关注**显示层**（浏览器/终端渲染、前端字体）与**尚未覆盖的实机输入通道**。若用户报告的是真实会话乱码，应取那段具体文字与其出现界面重新定位，不要再从 `persistence/atomic.py` 查起。回归护栏见 `tests/test_s03_encoding.py`。

现有原子存储已经使用 UTF-8 和 `ensure_ascii=False`。检查按以下顺序进行：

1. 读取原始字节并显式用 UTF-8 解码、解析 JSON，区分内容损坏、合法 JSON 转义和终端字体/代码页显示问题。
2. 使用同一条中文＋标点＋emoji 样本，比较 HTTP 入参、适配器输出、recent、时间索引以及实际送入模型的字符串。
3. 找到最早不一致的位置，修正该处解码或序列化；Windows shell 通过管道传入测试文本时也检查编码。
4. 已损坏历史记录从可追溯原文判断是否可恢复；历史修复作为显式数据操作处理，不做全目录猜测转码。

验收要求新输入在以上各层逐字符一致，事实输出中文正常；检查使用临时数据和指定样本，不把用户原文写入普通日志。

## 6. 召回优化

### 6.1 当前实现与预算

- 现有 `tokenize` 已使用中文二元/三元组及拉丁片段；首先收集漏召回样本，再决定是否更换分词。
- 召回代码分别计算 BM25 和可用候选向量相似度，再融合排序。向量路径依赖候选条目已有的 `embedding`。
- 当前查询向量按需请求注入端口；新提炼的事实和反思默认 `embedding=None`，独立流程缺少候选向量的生成与维护。
- 默认宿主向量适配器不可用时使用 BM25。事实是否能提炼与召回质量分别验收。
- `ContextRequest.budget_ms=1000` 是上下文构建预算；整轮还包含模型生成和持久提交。S05 的新系统性能验收使用 N14 指定的数据规模与期限。

所有增强共享上下文总期限，保留渲染和提交检查所需时间。可选步骤超时后返回原始检索结果；不隐藏实际降级原因。

### 6.2 先建立失败样本与基线

在脱敏固定样本中记录查询、预期命中、应排除项、主体/场景、近期会话和删除/更正状态，覆盖：

- 中文实体与短词、同义表达；
- “你刚才说的那个”等指代与话题延续；
- 新话题切换、无关内容抑制；
- 跨主体、跨场景隔离与已删除内容。

每次只改与失败类型对应的策略，比较 Recall@K、无关注入、重复提及及 p50/p95 延迟。性能记录注明数据规模、候选数、硬件、并发和缓存冷热状态；隔离边界和删除规则是硬性通过条件。

先复用现有指代、近期会话和关键词逻辑。专业分词、查询扩展和向量是可选择的改进，不设置“必须全部做完”的串行依赖。

> **S06 已建立基线（2026-10-24）**：样本在 `tools/s06_samples.py`（8 案、17 条合成事实，覆盖上文全部失败类型），测量在 `tools/check_s06_recall.py`，报告在 `tools/s06-recall-baseline.json`，回归门槛在 `tests/test_s06_recall_samples.py`。基线（BM25、无向量、顺序执行）：Recall@K **0.857**、无关注入 **0**、删除泄漏 **0**、重复提及 **0**、硬失败 **0**；召回 p50/p95 ≈ **0.69/2.00 ms**，被动上下文 ≈ **0.81/1.26 ms**。唯一的已知缺口是**同义表达**（“失眠”对“熬夜”），这正是 §6.3 查询扩展或 §6.4 向量要解决的问题；S07 是否启动取决于该缺口是否值得付出额外模型/索引成本。
>
> 测量时确认的一条约束：**指代补全只存在于被动路径**（`build_turn_context`），显式 `recall_memory` 不做展开（见 §6.2 所说的两条独立链路）。样本因此带 `path` 字段声明被测链路，新增样本时必须写明，否则会用错链路得出假结论。

### 6.3 可选查询扩展

默认关闭模型查询扩展。仅在有明确同义表达或指代失败、现有确定性逻辑仍不足时评估。

- 与原查询一起检索，扩展词不写入事实，也不改变主体、场景或时间范围。
- 额外模型调用计入上下文总期限、调用次数和成本；不能认为使用已有模型就没有新增延迟。
- 保留原查询结果，扩展超时或失败立即使用已有结果；最终仍按相关性、屏障和预算裁剪。
- 缓存扩展时，键包含影响改写的会话上下文、模型及版本，受删除/更正失效约束；不跨主体复用带私人上下文的结果。
- 验收同时记录命中改善、无关注入和延迟增量，收益不足时保持关闭。

对话生成所需的模型调用属于正常路径；其他远程增强是显式可选项，均有独立期限并服从总预算。

### 6.4 可选向量：同时解决查询与候选编码

只增加查询编码器无法让 `embedding=None` 的新事实参与向量排序。BGE 的[官方使用说明](https://huggingface.co/BAAI/bge-small-zh-v1.5)也分别编码 query 和 passage，再计算相似度。

首个向量实现采用**可重建、有界的候选向量内存缓存**，由后台批量填充；不把模型推理塞进持久提交事务：

1. 对当前候选事实、反思及允许召回的人格条目编码，按条目 ID、文本哈希和模型空间标识缓存。
2. 查询侧只计算当前查询向量。候选缺失、尚未完成编码或缓存被淘汰时，该条目保留 BM25 路径。
3. 后台编码的候选范围沿用现有范围和容量规则，不强制只取 BM25 命中的 TopK，以免同义漏召回仍被排除。
4. 重启后后台重建，冷启动时使用 BM25；健康状态报告向量可用性、候选覆盖率和缓存容量。
5. 既有条目携带的持久向量仅在模型空间与文本版本匹配时使用；新增持久缓存留待重建成本确实成为问题后评估。

模型空间标识包含模型版本、维度、归一化/池化与量化配置；维度相同也可能属于不同空间。查询和候选必须使用兼容的同一空间。

删除、更正、文本修订及换模型都使相关候选缓存失效。后台写回前复查文本版本和屏障代次，查询输出前再过滤；查询缓存有界并纳入适用的删除范围。

#### 选型与打包

`bge-small-zh-v1.5` 可作为首个中文候选；只有本地样本收益值得额外成本时再比较 base 或其他模型。选型记录实际 CPU、推理后端、精度、线程数、文本长度、批量、冷启动、稳态 p95 和进程内存，不预设固定延迟或把权重大小当成总内存。

优先评估可选 ONNX 适配器，核心默认安装不依赖推理运行时。模型文件使用明确的本地目录，不进入 wheel、sdist 或 Git；启动对话时不自动下载。交付组件要包含 tokenizer 配置、模型版本/校验值、许可证、查询前缀、池化和归一化约定。

模型缺失、加载失败、推理超时或资源不足时使用 BM25 并暴露原因。加载和 CPU 推理不得阻塞事件循环；取消后的后台工作受有界执行器管理。

验收分别检查：无模型时保持基线；有模型时指定样本改善；冷启动和超时仍能回复；删除、更正及模型切换后旧向量不参与结果。

### 6.5 本次不引入

- 向量数据库、专用索引服务和图存储；
- 无失败样本支撑的分词替换或每轮模型查询扩展；
- 以吞掉人格、权限、删除和存储错误实现的“无感降级”。

是否扩大存储或索引能力，以候选规模、重建耗时和实际质量结果决定。

| 外部任务调度与游戏控制 | 记录相关经历 | 沿用现有宿主/插件调度 | 负责实际执行及结果 |

服务不新增通用执行器或任务代理。客户端只调用所需接口；请求任务继续走原调度通道，执行结果再按来源和范围进入记忆。

人格消费者的 pending/adopted/failed、planner 配对及真实送达语义继续沿用当前合同。数据已落盘、上下文已取到、模型已使用和用户已收到分别记录。

### 8.1 2026-10-24 实现复核：接入前需要修复的七项问题

**结论（2026-10-24 修复后）：七项 P1 已全部修复并验证，S02/S04 回到已完成，可进入 S05 联调。** 修复均有走真实服务装配与 HTTP 调用链的行为测试：`tests/test_s05_review_fixes.py`（17 项，按 R01—R07 分组）。

**原结论（修复前）：服务骨架、接口和存储组件已经具备，S02/S04 的提交与运行闭环仍需修正，再进入 S05 联调。** 以下七项均为 P1：已在临时数据根、合成内容和替身模型下复现，分别影响删除、单写者、范围隔离、故障恢复、对话完整性和服务持续可用性。本节记录问题与验收条件，批次状态统一维护在 roadmap §2.2。

复核时运行 `tests.test_s02_turns` 与 `tests.test_s04_service`，现有 **38 项全部通过**；额外故障注入复现了下列缺口。修复时应将对应复现固化为行为测试，重点走真实服务装配与 HTTP 调用链，避免只手动调用内部失效方法或只测固定时钟。

#### R01：删除、更正与请求结果失效没有完整接线（S02/S04）

**已修复**：`domain/turn_results.py` 的 `TurnResultCleaner` 作为删除步骤 `turn_results` 运行（已计入 `CONTENT_STEPS`），`CorrectionTurnInvalidator` 接入更正派生失效链；`TurnRecord` 持久化 `subject`。验收测试走真实 `forget()`，断言 410 且记录正文已清空。

- **现象**：先通过 `/v1/turns` 提交含回复的轮次，再调用真实 `deletion_service.forget()`，删除回执为 `completed`，查询请求结果仍返回 `committed` 和旧回复正文。生成依据检查 `_basis_moved()` 也固定返回 `False`。
- **位置**：[composition.py](../src/rin_memory/adapters/composition.py) 的删除/更正装配、[turns.py](../src/rin_memory/domain/turns.py) 的 `invalidate_sources()`、[server.py](../src/rin_memory/service/server.py) 的 `_basis_moved()` 与 `request_status()`。已有失效方法尚未接入实际删除/更正流程；手动调用该方法的测试绕过了缺口。
- **修复要求**：实际删除/更正必须联动请求结果、上下文凭据及相关缓存；生成和提交之间复查使用的来源、范围与版本。失效结果清除正文，仅保留去重与屏障所需标识。
- **验收**：从实际删除/更正入口操作后，结果查询和同键重试均不返回失效正文；生成途中失效应终止提交或重新获取有效依据；重启及 journal 回放后仍保持失效。删除结果按合同返回 410。

#### R02：服务停机时提前释放根锁，旧请求仍能写入（S04）

**已修复**：`stop()` 先递增代次拒绝新请求，再用 `_drain` 以线程事件等待在途请求结束（默认 30s 上限，超时如实报告 `abandoned`），然后停后台、最后释放根锁；`assert_current()` 在提交前拒绝失去代次的请求。`begin_request()` 会清 `_drained`——原实现事件初始为 set，导致排空立即返回，这是测试抓到的真实缺陷。

- **现象**：让 `/chat` 的模型调用挂起，调用 `MemoryService.stop()` 后，新服务可取得同根所有权；再放行旧模型，旧请求仍提交成功。两个所有者的写入期发生重叠。
- **位置**：[memory_service.py](../src/rin_memory/service/memory_service.py) 的 `stop()`、[server.py](../src/rin_memory/service/server.py) 的 HTTP 请求线程与服务退出顺序。当前仅停止后台维护，未排空在途生成/提交。
- **修复要求**：退出先关闭新请求入口，等待或取消在途请求，并等待实际工作结束；所有写任务结束后再释放根锁。已失去本代运行资格的请求禁止继续提交，取消协程时同时处理仍在运行的线程任务。
- **验收**：挂起模型或提交的情况下发起停机，锁在旧写任务结束前始终不可被接管；新实例取得锁后，旧实例不得新增记录；正常退出与强制中断后的恢复分别覆盖。

#### R03：HTTP 层丢失主体与场景边界（S04）

**已修复**：`subject/scene/session_id/client_id` 贯穿上下文构建、`context_receipt_id` 摘要与 `request_status` 查询；`TurnRecord` 新增 `subject`，跨主体查同一 request_id 按“未知”处理，不泄露存在性。

- **现象**：查询同一条私有事实，直接调用核心并传 `subject="group:other"` 时无结果；向 `/v1/context` 传相同主体时，API 仍返回该私有事实。接口读取了文本，但未把主体/场景完整传入核心上下文构建。
- **位置**：[server.py](../src/rin_memory/service/server.py) 的 `context()`、`_build_turn_request()` 和 `request_status()`，以及请求指纹与结果查询范围。
- **修复要求**：将 character、subject、session、scene 及来源适用范围贯穿上下文、人格投影、生成、入库、去重和结果读取；明确 client_id 的来源身份与访问边界，防止切换客户端或主体后误复用其他范围的结果。
- **验收**：用同一组事实分别走核心和 HTTP 入口，私聊/群聊、宿主/游戏/run 的排除结果一致；跨主体的同 request_id/turn_id 不串用正文；游戏专属内容不进入通用人格或宿主上下文。

#### R04：入队失败后的重试因时间戳变化变成来源冲突（S02，涉及 S03 的 ingest 修复）

**已修复**：`ingest_turn(occurred_at=...)` 接受稳定业务时间并随记录持久化，重试复用首次值；`_persist` 捕获 ingest 异常后标记 `failed`（可重试），不再留下 `pending` 被误判为并发。内容真变化仍返回冲突。

- **现象**：使用默认时钟，在原文保存后让 `outbox.enqueue()` 抛出异常；重启并重试同一请求，得到 `failed / source_key_reused_with_different_payload`，待处理队列仍为 0。
- **位置**：[extraction.py](../src/rin_memory/domain/extraction.py) 的 `ingest_turn()` 每次重新生成 `occurred_at`；[records.py](../src/rin_memory/persistence/records.py) 的来源指纹包含该字段；[turns.py](../src/rin_memory/domain/turns.py) 先 ingest 再提交整轮 journal。
- **修复要求**：首次接收的业务时间与规范化输入在重试/恢复时保持稳定；让来源登记、原文、提炼意图与请求状态可幂等续作。固定 `occurred_at` 的语义或复用首次登记值，不能简单忽略真实内容变化导致的来源冲突。
- **验收**：故障注入后推进时钟、重启并重试，最终只有一轮原文、一个有效提炼任务和一个提交结果；响应丢失后的重放不重复生成；真正修改消息内容仍返回冲突。

#### R05：`/chat` 生成没有使用记忆上下文，生成回复未进入整轮历史（S02/S04）

**已修复**：`_generate` 先按请求范围构建 `build_turn_context` 并把渲染块注入 system 消息（失败降级为空块，不让整轮失败）；服务生成的回复以 `ai` 消息追加进 recent/原文，外部已完成轮次不重复追加。

- **现象**：在核心上下文入口放置可观测替身，`/chat` 成功后调用次数为 0；recent 只有传入的 human 消息，生成的 assistant 回复只存在于请求结果表。
- **位置**：[server.py](../src/rin_memory/service/server.py) 的 `_generate()` 只拼人格卡与输入消息；[turns.py](../src/rin_memory/domain/turns.py) 的 `_persist()` 只把 `request.messages` 交给 ingest。
- **修复要求**：生成前按范围构建人格、更正、近期对话及可选召回上下文，并遵循 §3.3 的预算和降级顺序。服务生成模式将 assistant 回复纳入完整轮次原文/recent/后续提炼；外部已完成轮次按传入消息提交，避免重复追加回复。实际送达另行记录。
- **验收**：先存入相关事实与更正，再调用 `/chat`，模型输入包含有效上下文；提交后 human/assistant 角色与顺序完整，重启和重试不重复轮次；未送达的回复不被标记为已送达。

#### R06：一次瞬时模型故障会持续关闭聊天能力（S04）

**已修复**：只有 `config`/`auth` 这类不可恢复错误才 `degrade_chat()`；`timeout`/`rate_limit`/`transport` 记入 `last_model_error` 并保持 `chat_ready`，下次请求可成功；已提交结果回放不受模型可用性影响。

- **现象**：替身模型首次 timeout，随后恢复正常；第二次 `/chat` 仍返回 `chat_unavailable`，模型调用总次数为 1，`chat_ready` 始终为 false。
- **位置**：[server.py](../src/rin_memory/service/server.py) 在所有 `ModelCallError` 上调用 `degrade_chat()`，后续请求在调用模型前被拒绝；能力刷新仅在启动时发生。
- **修复要求**：区分缺配置/鉴权错误与可恢复的超时、限流、传输故障；给可恢复故障提供有界重试或探测恢复路径，保留错误类别与 retryable 语义。已提交请求的结果回放独立于当前模型可用性。
- **验收**：模型故障→恢复后，无需重启服务即可成功生成；限流遵守等待与容量限制；模型离线期间已提交结果仍可回放，存储与管理能力保持可用。

#### R07：逐请求事件循环与共享信号量冲突，超时会突破并发上限（S04）

**已修复**：适配器改用 `threading.BoundedSemaphore`，在提交工作线程前获取、由工作线程自身释放，跨事件循环不再报 `bound to a different event loop`；超时后底层线程继续占槽位，实测 peak 并发严格等于配置上限。

- **现象一**：HTTP 请求分别执行 `asyncio.run()`，共享 `HttpModelInvoker` 内的 `asyncio.Semaphore`；跨两个事件循环执行发生竞争的批次后，出现 `Semaphore ... is bound to a different event loop`。
- **现象二**：配置并发上限 1，让底层 HTTP 工作线程阻塞，两次调用分别超时后仍有 2 个线程同时工作。协程退出释放了信号量，`to_thread()` 内的实际请求继续运行。
- **位置**：[server.py](../src/rin_memory/service/server.py) 的 `_run()`、[model_http.py](../src/rin_memory/adapters/model_http.py) 的 `invoke()`。
- **修复要求**：服务共享异步资源由一个长期存活的事件循环管理；对实际模型请求实施有界并发与排队期限。调用方超时后，底层工作仍占用容量直到结束；停机应跟踪并排空这些工作。
- **验收**：经真实 HTTP 入口连续运行多批并发请求，不出现跨循环异常；在超时/取消条件下测量实际在途调用，峰值始终不超过配置上限；队列等待和退出时间符合设定期限。

建议修复顺序：先 R07/R02 统一运行与退出，再 R03/R01 补范围与失效，随后 R04/R05 补提交链路，最后 R06 完成故障恢复。R01、R04、R05 回填 S02；R01—R03、R05—R07 回填 S04。S03 分类/编码成果与 S06 核心召回基线继续保留，HTTP 范围隔离另按 R03 验收。
